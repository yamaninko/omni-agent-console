Multi-Agent Studio Workflow

The OmniAgent Console is a pipeline studio powered by OpenAI-compatible LLM APIs (NVIDIA NIM by default). It orchestrates complex developer tasks by passing them sequentially through a specialized chain of AI agents:

1 Planner Agent

Analyzes your prompt and the selected skills, establishes concrete goals, and outputs a structured execution plan.

2 Research Agent

Extracts facts, constraints, and technical context from the supplied prompt to lay the foundation for the plan.

3 Coder Agent

Runs as an agentic tool loop (like Claude Code): the model calls write_file / read_file / list_files to build the project file by file directly in the workspace, following the selected skill conventions. Every tool call streams live to the console.

4 Reviewer Agent

Reviews the generated output for correctness, security, and skill-convention violations, producing prioritized findings.

4b Fix loop (optional)

If the Reviewer produces actionable findings, the Coder runs one extra tool-loop pass to patch only those items (Fix loop started / Fix loop skipped in the console).

5 OpsMonitor Agent

Summarizes execution health, usage signals, latency considerations, and operational risks of the run.

Moderated Panel (Debate)

Panel is a second product surface next to Studio: a moderator + commentators cast debates a topic with automatic floor order, saved sessions, and Markdown transcripts.

1. Configure the cast (Groups)

  • Open Groups (/groups or /groups/{guid}).
  • Add speakers with Role (Moderator / Commentator), Stance (Neutral / For / Against / Custom), persona prompt, and model.
  • Speaking order = moderators first, then sort order. Use Clone group or Open in Panel when ready.

2. Run a session (Panel)

  • Open Panel, pick the group, optional title, topic (or a sample topic chip).
  • Choose 1–3 rounds (full roster passes), then Start panel.
  • URL becomes /panel/{session-guid} — bookmarkable. Stream shows a roster briefing, floor grants, and speeches. Default filter is Conversation (hides model noise); switch to All events for diagnostics.
  • While running you see is speaking…, a floor progress bar, and remaining seconds. If status stays Pending, a queue hint explains worker backlog (Studio tasks share the worker).
  • After finish: Continue with a follow-up, Export .md, Read (browser TTS) on each speech, or Clear finished bulk-delete.
  • Roster briefing is collapsed by default — expand when you need the cast card.

3. Keys & durability

Settings → OmniAgent / NVIDIA API key is required. Keys are written to Vault and mirrored under ./data/secrets so a Vault -dev restart does not wipe lab credentials. Home shows whether the key is configured (and a masked preview when available).

Using the Studio

1. Workspace Path & Prompt

On the Studio page, first pick a workspace subfolder (e.g. /workspace/my-api) — generated files land there, mapped to the repository's workspace/ folder on your host. Then write your prompt describing what to build.

2. Skills — Automatic & Manual Selection

As you type, the console matches your prompt against the Skill Library and auto-selects fitting skills — they appear as ✨ dashed chips with a "N auto" counter. Click any chip to read what it does; click an auto-selected chip to dismiss it, or click unselected chips to add them manually (manual picks are remembered across sessions). If the prompt leaves the stack or datastore ambiguous, the console shows follow-up questions (e.g. "Which language/framework?") — refine your prompt or pick the skills yourself.

3. Running & Watching

Click Run Task. The live console streams every agent step via WebSockets: skill injection ("Applied N skill(s)"), each Coder iteration, and every filesystem tool call as it happens — e.g. 🔧 Wrote app/main.py (886 chars) — ending with a "Coder wrote N file(s) via tools" summary. Browse results on the Workspace page; metrics live in History, Task Detail, and Dashboard.

4. Controlling Executions

  • Cancellation: Cancel halts the active run within about a second — the request reaches the worker over Redis and aborts even an in-flight model call; the task is finalized as Cancelled.
  • Rerunning: Failed/cancelled tasks show a Rerun button that clears prior logs and restarts fresh.
  • Crash safety: If the worker restarts mid-run (deployment, crash), the queued message is automatically redelivered and the task re-executes — no run is silently lost.

Skill Library

Skills are reusable convention packs injected into every agent's system prompt as mandatory rules for that task. They turn vague prompts into properly structured projects (real package manifests, layered folders, Dockerfiles, READMEs). 21 skills ship out of the box:

  • Backend: Node.js + Express + TypeScript, Go REST API, .NET Web API, Java Spring Boot, Python FastAPI
  • Frontend: Angular, React (Vite), Flutter
  • Data: PostgreSQL + Migrations, Relational DB + ORM, MongoDB, Redis Caching, RabbitMQ Messaging
  • Security: JWT Authentication (bcrypt, token middleware, env secrets)
  • Quality: Input Validation (Zod/Joi), Unit Tests, REST API Conventions, Health Checks & Observability, Swagger / OpenAPI (UI + openapi.json examples), Project README & Docs
  • Packaging: Dockerized Service (multi-stage build, compose, healthcheck)

Manage them under Settings → Skill Library: add your own skills, edit instructions, and tune the comma-separated keywords field — keywords drive the prompt-based auto-suggestion, so custom skills become auto-suggestable too.

Fallback chains

Each agent supports up to two fallback models (Agents page). When the primary model fails — timeout, rate limit, 404, provider error — the orchestrator automatically retries the same call on the next model in the chain and logs a "falling back" console event. Only auth failures (401) stop the chain, since the same key applies to every model. Free-tier latency varies with load, so pairing each primary with fallbacks from different families keeps runs resilient.

Currently applied chains (primary → fallback 1 → fallback 2):

  • Planner: gpt-oss-120b → nemotron-3-super-120b-a12b → llama-3.1-8b-instruct
  • Research: nemotron-3-super-120b-a12b → step-3.7-flash → llama-3.1-8b-instruct
  • Coder: deepseek-v4-flash → gpt-oss-120b → nemotron-3-super-120b-a12b (timeout 300s)
  • Reviewer: gpt-oss-120b → nemotron-3-super-120b-a12b → deepseek-v4-flash (timeout 180s)
  • Ops Monitor: llama-3.1-8b-instruct → step-3.7-flash → minimax-m3

Settings & Keys Configuration

Navigate to the Settings page to configure system-wide parameters:

  • OmniAgent API Key: Your NVIDIA NIM key, stored in Vault (with an OMNIAGENT_API_KEY environment fallback).
  • API Credentials Manager: Additional provider keys (OpenAI, Anthropic, Gemini, Ollama, Custom). Keys are write-only — the API returns only a masked preview (sk-t...cdef); leaving the key blank while editing keeps the stored one. System Architecture & Topology

The OmniAgent Console utilizes a decoupled, worker-oriented on-premise architecture designed for high throughput and security:

Architectural Implementation Details

1. Cross-Process Live Log Streaming

The Worker and the API run in separate containers. Because WebSockets (SignalR) require stateful client connections, clients connect directly to the API container. The worker publishes console events to a Redis Pub/Sub channel; the API's RedisConsoleEventSubscriber forwards them to the appropriate SignalR task group.

2. At-Least-Once Task Delivery

RabbitMQ consumption uses manual acknowledgements. The orchestrator distinguishes user cancellation (task finalized as Cancelled → message ACK'ed) from host shutdown (task left Running, exception rethrown → message NACK'ed and requeued, so the run re-executes when the worker returns). Ack/nack always goes through the exact channel that delivered the message — delivery tags are channel-scoped, and a dead channel means the broker already requeued. Dangling agent runs from an interrupted attempt are closed on redelivery.

  • Poison-message guard: a redelivered message that fails unexpectedly a second time is finalized as Failed and ACK'ed instead of requeueing forever — effectively max two delivery attempts.
  • Startup recovery scoping: the API's "mark Running tasks as Failed" recovery runs only in single-process mode (no RabbitMQ). With a separate worker, an API restart never touches live runs — genuinely dead runs are covered by queue redelivery.

3. Cross-Process Cancellation

The API and the worker are separate processes, so an in-memory cancellation token registry alone cannot stop a run. Cancel now works in two layers: the API writes Cancelled to the database first, then publishes the task id to the Redis task-cancellations channel; the worker's RedisTaskCancelSubscriber cancels the local token, aborting the in-flight model HTTP call within a second (verified live). Writing the status before firing the token ensures the worker classifies the interruption as a user cancel (ACK) rather than a shutdown (NACK/requeue). As a belt-and-braces fallback, the Coder tool loop also re-checks the task status from the database at every iteration.

4. Model Fallback Chains

Each agent's model list is resolved into a chain (BuildModelChain): the primary DefaultModel followed by up to two comma-separated FallbackModels, de-duplicated case-insensitively. On a ProviderException the orchestrator advances to the next model for every error code except Unauthorized (ShouldFallbackToNextModel) — timeouts, rate limits, 404/InvalidModel, and provider outages are all model-specific, while a 401 would fail identically across the chain. Each switch updates the model call log and emits a "Model X failed (code); falling back to Y" console event, so the run history always shows which model actually produced the output. Per-model retries (with exponential backoff) still apply before the chain advances.

5. Agentic Tool Loop (Coder)

The Coder no longer produces the whole project in a single completion. It runs a tool-calling loop (the same pattern agentic CLIs like Claude Code use): the model is given three function tools — write_file(path, content), read_file(path), list_files(path?) — via the OpenAI-compatible tools parameter. Each iteration is one short chat completion; when the model requests tool calls, the worker executes them (AgentWorkspaceTools), streams a 🔧 console event per call, feeds the results back as tool messages, and continues. When the model answers without tool calls, that answer is the final summary. Hard limits: 24 iterations, 50 files per task, 1M chars per file. After the Reviewer, a single optional fix loop may re-run the Coder with a findings-only objective (ReviewerFixLoopPolicy): console shows Fix loop started or Fix loop skipped (no findings). OpsMonitor always runs last.

  • Per-iteration accounting: every iteration is its own model call log entry — token usage, latency, and cost stay accurate.
  • Sticky model: each iteration's fallback chain starts from the model that last succeeded, so a dead primary isn't re-tried every round (HTTP 410 "model removed" now maps to InvalidModel).
  • Graceful finish: if the whole chain fails mid-loop but files are already written, the run completes with a warning instead of discarding the work.
  • Legacy fallback: models without function-calling support still work — their final answer goes through the old fence/filepath: exporter, and blocks with no detectable filename land in an output/ subfolder.

6. Workspace Path Guard & Code Export

Every filesystem path — the user-supplied workspace folder, browser file reads/deletes, tool-call paths from the agentic loop, and even filenames extracted from model output — is resolved through WorkspacePathGuard, which confines it to the /workspace root: .. traversal, out-of-root absolute paths, backslash tricks, and symlinked components (including dangling symlinks) are rejected. The legacy exporter understands both fenced markdown blocks and fence-less // filepath: annotated streams, splitting them into real files (max 50 files per export, 1M chars per file; skipped blocks are reported in the console).

7. Skill Injection & Auto-Suggestion

Selected skill IDs travel in the task's context JSON. The orchestrator loads the enabled skills and appends their instructions to every agent's system prompt as a mandatory-conventions block. Suggestions come from SkillSuggestionEngine: whole-word keyword matching (letter/number lookarounds, so "go" never matches "django") plus follow-up questions when no Backend/Frontend skill matches or a database is mentioned without a specific Data skill.

8. API Authentication & Secret Handling

ApiKeyMiddleware validates X-Api-Key, Bearer, or SignalR ?access_token credentials using SHA-256 + FixedTimeEquals (timing-safe, no length leak). Provider credentials are write-only through the API — responses carry only apiKeyConfigured and a masked preview, and an empty key on update keeps the stored secret. The regex-based InputSanitizer redacts secrets from prompts, outputs, and error messages before they reach PostgreSQL logs: NVIDIA/OpenAI/Anthropic (sk-ant-)/Google (AIza)/GitHub (ghp_, github_pat_)/Slack tokens, JWTs, Bearer headers, and PASSWORD= / "api_key": "…" style assignments (value-only, keys stay readable). Infrastructure ports (Postgres, Redis, RabbitMQ, Vault, OpenSearch) bind to 127.0.0.1 by default via INFRA_BIND_ADDRESS, keeping secret-carrying services off the local network.

9. Reasoning-Model Compatibility

Some reasoning models write their entire answer into a reasoning / reasoning_content field and leave content empty. When content comes back blank, the provider now falls back to those fields, so reasoning-only models produce usable output instead of failing the run with an "empty response" error.

10. Deployment Profiles: Laptop vs Shared-Lab

The same codebase supports two profiles selected by the SHARED_LAB environment variable. Off (default): today's single-user behavior — one tenant, global workspace. On: classroom mode for one shared server — every browser generates a local session id (X-Studio-Session-Id); tasks are owned by their session (foreign task ids answer 404 everywhere, including the SignalR console stream), each session's workspace is confined to /workspace/sessions/{id}/ as its effective path-guard root, and configuration writes (credentials, agents, skills, settings, providers) answer 403 for students — the skill auto-suggest endpoint stays open. The console API key becomes the instructor credential: it bypasses session scoping and unlocks settings. As a fail-safe, the API refuses to start with SHARED_LAB=true and no CONSOLE_API_KEY, so an anonymous shared deployment cannot happen by mistake.

Cost & Usage Calculations

The system tracks token usage and calculates estimated cost dynamically upon each model API return. 

Cost = (InputTokens / 1,000,000 * InputPricePerMillion) + (OutputTokens / 1,000,000 * OutputPricePerMillion)

Prices are preconfigured based on the official pricing charts of Llama 3.1 and Nemotron models; unknown models fall back to a flat default rate.
